Abstract

This document defines a label structure that conveys information related to cybersecurity compliance with baseline security standards. The label is composed of a trademark and a mechanism (QR code) to link consumers to more detailed information. The detailed information is defined as JSON fields and in presentation form with an example in HTML. This standard was developed by the Consumer Technology Association’s R14 Cybersecurity and Privacy Management Committee. This is an approved and published CTA standard document. All CTA standards are available at CTA.tech/Standards.

              1. Scope

              The label outlined in this standard is intended to convey information related to cybersecurity compliance with baseline security standards. The label is composed of several layers. The on-package layer (Layer 0) is a binary on-package marking with multiple elements, first a trademark and secondly, a mechanism to link consumers to more detailed information on layers one and two.

              Layer 1 is intended to present consumer-friendly information supporting the product’s qualification according to assessment criteria. Layer 2 is intended to have a more technical focus, and present information more relevant to a sophisticated consumer user, or perhaps a professional cybersecurity user.

              This standard also defines how data fields are to be presented in order to ensure consistent display and a standardized format for communication in the API. 

              All intellectual property necessary to print and use the Full Mark or Technical Mark should be portable within the program scheme. Icons used in this standard (Section 4.2) are available at https://github.com/cta-source/standards/tree/main/cta-2120. This approach ensures portability in the situation where multiple third-party certifiers may be required to support program capacity and consistent presentation to end-users.

              4. Definitions, Symbols and Abbreviations

              4.1 Definitions

              Bounding Box: A graphic outline (“box”) intended to contain the elements of the Full Mark.

              First Linked Page (“Layer 1”): This page carries a limited amount of important security information suitable for the average consumer.

              Full Mark: A cybersecurity indicator used on consumer-visible packaging along with other branded product information; the Full Mark includes the Technical Mark and Trademarked Components.

              Module: The smallest element (black or white square) of the QR code.

              QR Code Zone Width: Linear distance necessary to contain the QR code and two quiet zones horizontally.

              QR Code Zone Height: Linear distance necessary to contain the QR code and two quiet zones vertically.

              QR Code: Follows the definition of GS1 QR Code, which is an encoding of element strings that does not support micro QR codes, nor the encoding of Kanji characters.

              Quiet Zone: Follows the definition from ISO/IEC 18004: This is a region which shall be free of all other markings, surrounding the symbol on all four sides. Its nominal reflectance value shall be equal to that of the light modules.

              Second Linked Page (“Layer 2”): This page carries information to support more technical users, researchers, and others who require such details.

              Technical Mark: A graphical component intended for application to or inclusion in the printed outer package (sometimes called the “gift box” in consumer products). The Technical Mark does not include the Trademark Components. It does include space for the Trademark Components, the QR Code and human-readable URL.

              Trademark Components: Identifying and protected (trademarked) graphical and/or text elements; the Trademark Components are out-of-scope for this technical standard except in as the standard defines allowable space.[1]

              Trademark Zone: Area within the technical mark that accommodates a scheme owner mark.

              Trademark Zone Width: Linear distance necessary to contain the Trademark components.

              Trademark Zone Height: Linear distance necessary to contain the Trademark components.

              URL Zone Height: Linear distance that defines the vertical space occupied by the human-readable URL Code and associated clearances.

              URL Zone Width: The linear distance that defines the horizontal space occupied by the URL Code and associated clearances.

              5. Overview

              This standard specifies a Technical Mark intended to be used as part of a Full Mark (which includes additional information). The Full Mark conveys to a consumer that the product meets certain cybersecurity requirements.

              Elements of the Full Mark include the following:

              • Full Mark
                • Trademark Components (out of scope for this document except as it defines allowable space)
                • Technical Mark
                  • Bounding Box
                  • QR Code

              6. Full Mark Design – Layer 0

              This section specifies the on-package design (the Technical Mark, excluding the trademarked components) with a QR code and a Bounding Box.

              The scope of this on-package design does not include use of the trademarked components when they are not accompanied by the QR code. For marketing reasons, the trademarked components may be placed separately in a prominent location, such as the front of the product packaging, with the same icon accompanied by the Technical Mark perhaps on the back of the packaging.

              6.1 Bounding Box Design

              The bounding box shall be a graphical element of an unfilled rectangular box, defined with a line of the darkest color available in the package design. Manufacturers should ensure color contrast to ensure readability given the expected distance and technology of the consumer.

              1. The bounding box shall be oriented vertically or horizontally. Whichever way it is oriented, the scheme owner’s mark or trademark must appear either above or to the left of the QR code as viewed on the package.
              2. The bounding box shall not violate the minimum quiet zone of the QR code.
              3. Bounding box must be sized to ensure legibility of the scheme owner mark and ensure QR code legibility with expected technology.
              4. Bounding box width is the sum of: 3x quiet zones + symbol width (or diameter) + QR code width.
              5. Bounding box height is the sum of two quiet zones + QR code height.

              The Full Mark will be divided into three zones: the QR Zone, the Trademark Zone, and the URL Zone.

              The Zones may be arranged in any of the following layouts:

              • Horizontal Layout (Figure 2):
                • The Trademark Zone must be placed immediately to the left of the QR Zone.
                • The Trademark Zone and QR Zone must have identical heights.
                • The URL Zone must appear below all other zones.
                • The width of the URL Zone must be equal to the full width of the label.
                • Vertical positions of the top edges of the Trademark Zone and the QR Zone must be identical.
                • Horizontal positions of the left edges of the Trademark Zone and the URL Zone must be identical.
                • Horizontal positions of the right edges of the QR Zone and the URL Zone must be identical.
                • The height of the URL Zone should be less than or equal to 20% of the height of the other Zones.
              • Vertical Layout A (Figure 3):
                • The Trademark Zone must be placed immediately above the QR Zone.
                • The URL Zone must appear below all other zones.
                • The Trademark Zone, QR Zone, and URL Zone must have identical widths.
                • Horizontal positions of the left edges of all Zones must be identical.
                • Horizontal positions of the right edges of all Zones must be identical.
                • The height of the URL Zone should be less than or equal to 20% of the height of the other Zones.
              • Vertical Layout B (Figure 4):
                • The Trademark Zone must be placed immediately above the QR Zone.
                • The Trademark Zone and QR Zone must have identical widths.
                • The URL Zone must appear to the right of all other zones, with text rotated 90° clockwise from horizontal.
                • The height of the URL Zone must be equal to the full width of the label.
                • Vertical positions of the top edges of the Trademark Zone and the URL Zone must be identical.
                • Vertical positions of the bottom edges of the QR Zone and the URL Zone must be identical.
                • Horizontal positions of the left edges of the Trademark Zone and the QR Zone must be identical.
                • The width of the URL Zone should be less than or equal to 20% of the width of the other Zones.

              General constraints:

              • The size of the QR Zone includes the Quiet Zone and the QR Code.
              • No zone may impinge upon or overlap the area of another zone.
              • The Label shall be rectangular.
              • The QR Zone shall be a square.
              • The Trademark Zone shall have an aspect ratio equal to that of the Trademark Components.
              • Adjacent Zones should be separated from each other by at least 0.5mm.

              Content:

              • Text in the URL Zone may be scaled or wrapped to fit in the allowed space.
              • Within the URL Zone, the URL text must be aligned left, right, or centered.
              • It is recommended to use a sans-serif, high-legibility font for the URL.
              • A five-point font should be considered a minimum size for legibility.

              Scaling:

              • The Label may be scaled as needed to accommodate the packaging design and the URL so long as the other constraints are met.
              • The Trademark shall be scaled to fill the Trademark Zone.
              • The QR Code, inclusive of the Quiet Zone, shall be scaled to fill the QR Zone.

              7. QR Code Design

              This section provides the requirements for the QR code (encoding, data density, relevant standard).

              This section considers usage requirements, such as placement, clear space required around the Full Mark, and color vs. black-and-white printing.

              Mark usage is typically defined in a license agreement related to a full cybersecurity label program. However, key usage details are defined here.

              The QR Code shall be comprised of the encoded character string for the URL or other resource identifier of the First Linked Page according to ISO/IEC 18004 [1]. The QR code size shall adhere to the ISO/IEC 18004 sizes ranging from 21 x 21 modules to 177 x 177 modules, which excludes micro QR sizes. The size of the QR Code shall comply to ISO/IEC 18004 and shall be comprised of modules at least 0.254mm x 0.254mm. The selected module size should be appropriate to the distance, lighting, and typical devices owned by readers. The code should be surrounded by four (4) modules on all four sides.

              The QR Code Quality should meet the following: [3] OR 1.5/(**)/660 where ** is the aperture size best matching the expected reading distance, as per ISO/IEC 15415 [2].

              The Mark may be presented in either light on dark or dark on light, depending on the surface intended to carry the Mark. In all printed versions, adequate contrast must ensure legibility for code and any human readable content.

              8. Overview of Linked Information Fields – Layers 1 and 2

              This section defines the information fields required for the “linked pages” pointed to by the QR code.

              The Label shall have two pages. A first page (Layer 1 or L1) shall be presented first and provide a link to a second page (Layer 2 or L2). Layer 1 is the initial “consumer-facing” presentation. Layer 2 provides additional information for advanced users, researchers or others. Both pages should be designed in accordance with industry accessibility best practices, including ensuring that all information is available via text-to-speech readers. 

              Layer 1 (consumer-friendly page): This page carries a limited amount of important security information suitable for the average consumer.

              Layer 2 (technical detail page): This page carries information to support more technical users, researchers, and others who require such details.

              A sample implementation of L1 and L2 in HTML/CSS may be found in Annex A.

              Figure 5 shows a sample of the on-line label presentation, Layer 1 (left) and second linked page, Layer 2 (right).

              8.1 Required Elements, Layer 1

              The first page shall incorporate the following elements.

              Title: This is the text, “Security Overview”.

              Program Mark: This is the trademark (certification mark) of the program.

              About This Label: This is the following text, “About This Label: This product is certified under the Federal Communications Commission U.S. Cyber Trust Mark Labeling Program. This product has been tested and approved to meet certain minimum cybersecurity standards. For more information about the U.S. Cyber Trust Mark Labeling Program, please visit: https://fcc.gov/cybertrustmark”. Note, this text may be modified or substituted at the discretion of the program owner.

              Language option: English or Spanish.

              Layer 1 Fields: These shall conform with the requirements in Section 9.2 First Linked Page (Consumer Page).

              8.2 Required Elements, Layer 2

              The second page shall incorporate the following elements.

              Title: This is the text, “Security Overview”.

              Program Mark: This is the trademark (certification mark) of the program.

              About This Label: This is the following text, “This page carries advanced information to support more technical users, researchers and others who require such details. To return to the basics page, see --link--.” The portion denoted as “--link--” shall be replaced with a hyperlink to Layer 1. Note, this text may be modified or substituted at the discretion of the program owner.

              Language option: English or Spanish.

              Layer 2 Fields: These shall conform with the requirements in Section 9.3, Second Linked Page (Technical Page).

              9. Field Definitions

              These field definitions are presented according to the following Structure of Field Definitions (section 9.1) and enumerated in the List of Field Definitions (section 9.2) that follows.

              9.1 Structure of Field Definitions

              This information clarifies elements of the List of Field Definitions section (section 9.2) that follows.

              9.1.1 Presentation Type

              This determines a presentation format as follows.

              9.1.1.1 Presentation Type: “General”

              The subheading is left-justified, in bold font, and followed by a colon (no spaces). On the next line the Field Value is in normal font and is left-justified and indented.

              Example:

              Support Period:

              No guaranteed support period.
              9.1.1.2 Presentation Type: “Simple”

              The subheading is left-justified, in bold font, and followed by a colon (no spaces). On the same line the Field Value follows in plain font. If the field requires more than one string (such as “Authorized By” or “Tested By”), strings shall be placed on separate lines.

              Example:

              Tested By: Ungoliant Laboratories

              http://ungoliantlabs.com/contact.html
              9.1.1.3 Presentation Type: “Non-Display”

              Non-display type fields are carried in the JSON Schema data but not displayed to the consumer or others.

              9.1.1.4 Presentation Type: “Mixed (image and text)”

              This format is only used for the sensor_data_collection field at this time.

              sensor_data_collection

              sensing Parameter Value

              description if has=true

              description if has=false

              icons

              images

              “This product can capture images or video.”

              “This product cannot capture images or video.”

              Links to ‘camera’ icon or ‘not camera’ icon (as appropriate)

              audio

              “This product can capture audio.”

              “This product cannot capture audio.”

              Links to ‘microphone’ icon or ‘not microphone’ icon (as appropriate)

              position

              “This product can determine location.”

              “This product cannot determine location.”

              Links to ‘compass’ icon or ‘not compass’ icon (as appropriate)

              9.1.2 Embedded Data Formats

              • URLs: URLs shall be strings in RFC 1738 format – i.e., the form “https://domain...”. URLs shall be limited to 256 characters including any terminating characters (e.g., null terminators if applicable).
              • Strings: Strings other than dates or URLs shall be of maximum length of 2048 characters.
              • Timestamps shall be a valid RFC 3339-formatted timestamp, in either “full-date” or “date-time” formats.
                • Example: yyyy-mm-ddThh:mm:ss[.s+]Z
                • Example 2: yyyy-mm-ddThh:mm:ss[.s+]-05:00 (for US Eastern Standard Time)
                • Example 3: yyyy-mm-ddThh:mm:ss[.s+]+09:00 (for Japan Standard Time)
                • Example 4: yyyy-mm-dd (“full-date” format)
                • Where: the "s+" represents 1 or more sub-second values.
                • The brackets denote that sub-second precision is optional, and that if no digits are provided, the decimal place shall not be present.

              9.2 First Linked Page (Consumer Page)

              This section defines the specific cybersecurity label parameters (“Fields”). These parameters are mostly specific to the manufacturer, product, lab and authorization body involved in this product certification.

              These Fields are presented alphabetically here. For the presentation of the Fields to the user or consumer, see section 8.

              9.2.1 Section: Label Header Information

              The Label Header is presented immediately below the Trademark Components on both L1 and L2 pages and carries the product and manufacturer names.

              9.2.1.1 Subheading: “Product Name”

              This Field is consumer-facing.

              Schema Field: product_name

              Presentation Type: Simple (note, for information on “Presentation Type”, see the above section Structure of Field Definitions).

              Field Value Type: String (note, for this and all strings, URLs and dates, see notes on lengths and formats in section “Embedded Data Formats”, above).

              Description: This is the product name found on the manufacturer's application for authorization to use the Mark. Other product names should be listed on the web page found at the Manufacturer's site.

              9.2.1.2 Subheading: “Manufacturer Name”

              This Field is consumer-facing.

              Schema Field: manufacturer_name

              Presentation Type: Simple

              Field Value Type: String

              Description: This is the Applicant (manufacturer) name found on the manufacturer's application for authorization to use the Mark.

              9.2.1.3 Subheading: “Product Model”

              This Field is consumer-facing.

              Schema Field: product_model

              Presentation Type: Simple

              Field Value Type: String

              Description: This is the consumer-facing alphanumeric identifier of the model of the IoT Product.

              9.2.2 Section: Security Information

              9.2.2.1 Subheading: “Sensor Data Collection”

              Schema Field: sensor_data_collection

              Presentation Type: Mixed (image and text)

              Field Value Type: The HTML representation requires an image and text (see 9.1.1.4). The JSON representation requires boolean values (see Section 10).

              Description: This is an icon- and text-based indication of the presence or absence of certain sensors such as microphone and camera. The text portion of this field, like the rest of the Label, is intended to be suitable for text-to-speech applications.

              9.2.2.2 Subheading: “Security Updates”

              Schema Field: support_date

              Presentation Type: General

              Field Value Type: String (date)

              Description: This field presents the date until which the manufacturer promises to issue software updates correcting critical security vulnerabilities (i.e., the minimum support period); alternatively, a statement that the device is unsupported, and that the purchaser should not rely on the manufacturer to release security updates. Note that this field is a date only (no time information). This field is inserted into the label string, “Security Updates: At least until <date>”, replacing the string “<date>”.

              9.2.2.3 Subheading: “Getting Updates”

              Schema Field: security_update_information

              Presentation Type: General

              Description:  This field contains two subfields:

              • update_default describes the default setting for how updates are performed.
              • update_options describes other settings which are available (but are not selected by default).

              This information is presented as a series of one or more strings. The first string is the value of the update_default subfield and the string “by default”. If update_options is not empty, each entry in update_options shall be appended.

              Subfields:

              Schema field: update_default

              Description: This field contains information on the default setting for how updates are performed.

              Schema field: update_options

              Description: This field contains information on optional settings for how updates are performed.

              Data Encoding Notes:

              The possible values for this field are fixed and defined as one of five possible strings as follows:

              <automatic_no> “Automatic – may not opt out”

              Consumer explanation: Device will automatically receive security updates. This setting cannot be changed.

              <automatic_can> “Automatic – may opt out”

              Consumer explanation: Device will automatically receive security updates. This setting can be changed if desired.

              <manual> “Manual”

              Consumer explanation: User needs to manually install security updates.

              <consent based> “Consent based”

              Consumer explanation: User will be asked whether to update the device.

              <no update> “No security updates”

              Consumer explanation: Device will not receive any security updates.

              <not disclosed>

              <other>

              Source [4], section 2.1, Security Updates.

              If the option “<other>” is selected, it requires an arbitrary string. However, if at all possible, the other fields should be used rather than crafting a similar message using “<other>”.

              9.2.2.4 Subheading: “Access Control”

              Schema Field: access_control

              Presentation Type: General

              Field Value Type: Enum (String)

              Description: This field presents a string of one or attributes that indicate how the device can be accessed and who is allowed to access it. See [4], section 2.2, Access Control for values. If the primary attribute is <password> (with the value, “Password”) and one of the #1 sub-attributes for <password> (as per below) applies, the string shall include “ - “ (space, en dash, space) appended to the primary attribute string, followed by the #1 sub-attribute string value. If the #1 sub-attribute value is “Factory default”, one of the two possible #2 sub-attributes (as per below) shall be similarly included by appending “ - “ (space, en dash, space) to the string, followed by the #2 sub-attribute.

              Data Encoding Notes:

              The possible values for this field are fixed and defined as one of six possible strings as follows:

              <password> Password

              Consumer explanation: Password is required to access the device settings or data.

              <biometric> Biometric

              Consumer explanation: User’s physical or behavioral characteristics are required to access the device settings or data.

              <MFA> Multi-factor authentication

              Consumer explanation: At least two factors are required to access the device settings or data, for example a password and a one-time code sent to a previously registered phone number.

              <passkey> Passkey

              Consumer explanation: Device supports the Passkey standard of simplified authentication.

              <no control> No control over access

              Consumer explanation: Anyone can access the device without a password or other authentication method.

              <multi account> Multiple user accounts

              Consumer explanation: To access the device, user needs to create an account; multiple user accounts may be created

              <single account> Required user account

              Consumer explanation: To access the device, user needs to create an account

              <optional account> Optional user account

              Consumer explanation: User may create an account, but it is not required.

              <no account> No user accounts

              Consumer explanation: Device does not support the creation of user accounts.

              <not disclosed>

              <other>

              Optional sub-attribute #1 for <password> (one of the following):

              <factory default> Factory default

              Consumer explanation: The credentials required to access the device have default values that are initially generated by the manufacturer.

              <user generated> User generated

              Consumer explanation: User needs to create their own credentials to access the device.

              Optional sub-attribute #2 for <factory default> (one of the following)

              <user changeable> User changeable

              Consumer explanation: User may change the credentials that are required to access the device (for security purposes, make sure to change all default credentials before using the device).

              <not user changeable> Not changeable by user

              Consumer explanation: User cannot change the credentials that are required to access the device.

              9.2.2.5 Subheading: “Securing This Product”

              Schema Field: securing_this_product

              Presentation Type: General

              Field Value Type: URL

              Description: This field presents a URL that leads to information regarding appropriate use of configuration settings for cybersecurity.

              9.2.2.6 Subheading: “General User Information”

              Schema Field: general_user_information

              Presentation Type: General

              Field Value Type: URL

              Description: This field presents a URL that points to the product's main page. If there is no suitable product main page, this field may be used to point to the manufacturer’s preferred site, such as a corporate home page.

              9.2.3 Section: Footer Information

              The Footer is presented below all other information on both L1 and L2 pages and carries authorization information including date, test lab and certification body.

              9.2.3.1 Subheading: “Authorization Date”

              Schema Field: authorization_date

              Presentation Type: Simple

              Field Value Type: String

              Description: This is the date of product certification and authorization as issued by the CLA and as reflected in the grant of Certification. Note that this field is a date only (no time information).

              9.2.3.2 Subheading: “Authorized By”

              Schema Field: authorized_by

              Presentation Type: Simple

              Field Value Type: String, String

              Description: This is two strings representing the name and contact information of the CLA that issued the authorization to use the Mark.

              9.2.3.3 Subheading: “Tested By”

              Schema Field: tested_by

              Presentation Type: Simple

              Field Value Type: String, String

              Description: This is two strings representing the name and contact information of the CyberLAB that generated the test report supplied to the CLA in the manufacturer's application for authorization to use the Mark.

              9.3 Second Linked Page (Technical Page)

              The second linked page shall have the following fields.

              9.3.1 Section: Header Information

              The Header on Layer 2 is identical to the Header on Layer 1. See Section 9.2.1.

              9.3.2 Section: Additional and Technical Information

              These fields are presented below the Header and the string “Additional and Technical Information” on the L2 label page.

              9.3.2.1 Subheading: “Deleting Device Data”

              Schema Field: ownership_transfer

              Presentation Type: General

              Field Value Type: URL

              Description: This field presents a URL that leads to information regarding purging data prior to the consumer relinquishing possession of the IoT Device in case of sale. This information is specifically in regard to deleting on-device accounts, such as in the case of removing the account and credentials for logging into a smart home device.

              9.3.2.2 Subheading: “Account Deactivation”

              Schema Field: account_deactivation

              Presentation Type: General

              Field Value Type: URL

              Description: This field presents a URL that leads to information regarding how to deactivate or remove user accounts related to the IoT Product, including on the device, cloud services, smartphone app or other IoT Product Component that may maintain such accounts.

              9.3.2.3 Subheading: “SBOM HBOM Available”

              Schema Field: sbom_hbom_available

              Presentation Type: General

              Field Value Type: Booleans (two values, one for SBOM availability and one for HBOM availability)

              Description: This field is a structure containing two Boolean values that represent "yes/no" responses. These values are the manufacturer's disclosure of whether they maintain a Hardware Bill of Materials (HBOM) and/or a Software Bill of Materials (SBOM). A Boolean value of “TRUE” is equivalent to “yes, it is maintained”.

              9.3.2.4 Subheading: “Encryption and Key Management”

              Schema Field: encryption_and_key_management

              Presentation Type: General

              Field Value Type: URL

              Description: This field presents a URL that leads to technical information intended for researchers or others looking for information about these elements.

              9.3.2.5 Subheading: “QR Code URL”

              Schema Field: QR_code_URL

              Presentation Type: General

              Field Value Type: URL

              Description: This field is used on the L2 page and contains a clickable hyperlink back to the L1 page. It is also in the JSON structure as part of the record of the product certification.

              9.3.2.6 Subheading: “Security Contact”

              Schema Field: security_contact

              Presentation Type: General

              Field Value Type: String

              Description: This field is a string that may be a valid email address or valid website URL. The field should provide an entry point for researchers or other third-parties to contact the manufacturer's security team – e.g., in the case of a third-party discovery of a zero-day exploit in the IoT Product.

              In the case of a URL, the URL should point to a machine-parseable “security.txt” file as per RFC 9116 [10].

              Examples:

              • "https://mydomain.com/security-contact-us"
              • "security@mydomain.com"
              • “https://cdn.products.mydomain.com/security.txt”

              9.3.3 Section: Footer Information

              The Footer on Layer 2 is identical to the Footer on Layer 1. See Section 9.2.3.

              9.3.4 Section: Non-Displayable Information

              This section covers information that is not displayed in the label but is carried in the Schema (see Section 10, Schema).

              9.3.4.1 Subheading: Schema Header Information

              Schema Field: “$schema”, “$id”, “$comment”, “title”, and “description”

              Presentation Type: Non-Display

              Field Value Type: Strings

              Description: The “$schema”, “$id”, “$comment”, “title”, and “description” fields are fixed and shall not be changed from the values presented in the corresponding fields in the source schema (see the link in the value of the $id field, section 10.3).

              9.3.4.2 Subheading: “Created”

              Schema Field: created

              Presentation Type: Non-Display

              Field Value Type: timestamp

              Description: The time at which this record (that is, this entire JSON structure including this field) was originally created. The creator can use any time it deems most appropriate as the time the record was created, but it shall have resolution precise to seconds, at minimum. The created property shall not be changed. When creating a new version of this record, the original value is used.

              9.3.4.3 Subheading: “Modified”

              Schema Field: modified

              Presentation Type: Non-Display

              Field Value Type: timestamp

              Description: The time that this particular version of the record (that is, this entire JSON structure including this field) was last modified. The creator can use any time it deems most appropriate as the time that this version of the record was modified, but it shall have resolution precise to seconds, at minimum. The modified property shall be later than or equal to the value of the created property. If created and modified properties have the same timestamp, then this is the first version of the record.

              9.3.4.4 Subheading: Schema Version

              Schema Field: schema_version

              Presentation Type: Non-Display

              Field Value Type: String

              Description: This field is of the form “1.0.0” and indicates the schema revision number. The string must match the schema_version string in the version of the on-line schema used.
